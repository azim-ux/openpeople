# Security scope

Version 0.7.0 adds private operator enrollment and hashed, single-use MFA recovery codes. Codes require fresh authenticator proof to generate, are never saved in plaintext or idempotency records, and are discarded in backup snapshots/restores. Password changes invalidate codes; recovery use revokes other sessions. Generate codes again after restoration. The clean GitHub source export excludes live workspaces and private test logs; see [the release guide](docs/GITHUB_RELEASE.md).

OpenPeople 0.8.0 is designed for a single organization on a trusted local host. Default access is loopback HTTP. Remote use requires the configured HTTPS origin and a reverse proxy, preferably reachable only through a private VPN. The original findings, follow-up code blockers and three further payroll/SSO findings have regression fixes; this is not an enterprise deployment approval, independent security certification or a claim of equivalent protection to Workday. See the [latest deployment review](docs/DEPLOYMENT_REVIEW_0.8.0.md) for evidence and remaining installation gates.

Version 0.8.0 adds server-enforced Core HR scope before request replay, narrow report/role/policy boundaries, and exclusive private installation/recovery evidence. Recovery checks compare a frozen data fingerprint and retained audit anchor, verify encrypted authenticators are usable, and keep physical-device custody unverified. See [Core HR acceptance](docs/CORE_HR_RELEASE.md).

## Implemented controls

- Local bootstrap proof: setup needs the random token in an owner-only file. Setup closes after initial administration is created. Hostnames are explicitly allowed; supplied origins must match.
- Passwords: PBKDF2-HMAC-SHA256, 600,000 iterations and random 128-bit salts. Known and unknown accounts perform one password verification. This removes the reproduced large timing difference; it does not guarantee perfectly indistinguishable response timing.
- Sessions: random tokens stored as SHA-256 digests, HttpOnly/SameSite=Strict cookies, 30-minute human-inactivity and eight-hour absolute expiration; read-only polling does not renew activity. Trusted browser input sends a throttled activity heartbeat, and session expiry clears private modal/payroll caches. Users can inventory and revoke other sessions. Secure cookies are set in configured HTTPS mode. Deactivation, role changes, local recovery and password changes revoke sessions; reactivation requires fresh authentication.
- Authenticator MFA: six-digit RFC 6238 TOTP, encrypted secrets, replay counter checks, optional organization-wide requirement, restricted enrollment sessions and recent-authentication enrollment. Local MFA is also required after SSO when enabled. Recovery requires trusted local filesystem access and is audited.
- SSO: optional configured HTTPS OIDC issuer, authorization code with PKCE S256, browser-bound state, nonce, signed RS256/ES256 tokens, issuer/audience/expiry checks and verified email. Accounts must already be provisioned; SSO never grants a new role automatically. Token and metadata requests validate TLS and have timeouts.
- Authorization: fixed server-enforced roles and record ownership, manager direct-report scope, independent request approval, peer-only pay deduction edits and payroll finalization by a reviewer who neither created nor edited the run. Payroll edits/approval require the reviewed version. UI visibility is additional convenience, not the authorization boundary.
- External payroll: exact bounded result format, currency/employee/month binding, integer component totals, mandatory reviewed version, peer edits, retained maker exclusions and immutable finalized snapshots. Imported provenance is audited and recovered with the snapshot. Provider legality and tax calculations are not certified by arithmetic validation.
- Availability: SSO starts/callbacks share a nonblocking concurrency budget that reserves normal HTTP workers during a provider outage. Excess sign-ins return 503; provider unavailability can still interrupt SSO.
- Requests: parameterized SQL, validated bounded identifiers/text/currency, JSON bodies limited to 16 KB, CSRF tokens on authenticated writes, idempotency keys scoped to account/path/payload, bounded request handling. Unfinished bodies are handled before a database write transaction.
- Serving: Waitress CLI with eight worker threads, 100-connection cap, body/header limits, five-second unfinished-request deadlines, bounded pending budgets (48 total / 16 per backend peer), oldest unfinished-input eviction and hidden tracebacks. Behind Caddy all upstream connections share the loopback peer budget; it is not a per-VPN-user proxy connection quota. Remote mode trusts forwarding of scheme/address only from one loopback proxy and rejects HTTP. Keep Caddy and Waitress on the same host; do not expose Waitress directly.
- Rate limits: per IP, per minute, 10 login/setup requests, 10 MFA requests, 30 SSO requests and 180 general API requests. Limits are in-memory for one process and shared by clients using the same public address; a restart resets those IP limits. Ten failed sign-ins per normalized account in five minutes are additionally limited in SQLite, including unknown accounts; recovery after this short lockout is by waiting or local administrator recovery.
- Browser output: HTML escaping, CSV formula neutralization, CSP, anti-framing, MIME-sniffing protection, no-store responses and an explicit static file allowlist. No third-party analytics/scripts are required.
- Audit: business before/after values with passwords/authenticator secrets excluded; login successes/failures, MFA, SSO, access changes and recovery events. HR/auditors can inspect recent events and export bounded date/page ranges. Policy before/after values, access denials, export outcomes and privileged backup operations are recorded; complete retained tables are in backups. Separate SHA-256 chains and SQLite triggers reject ordinary event/seal edits. Independently retained anchors allow later prefix/rollback checking. Logs are local and not tamper-proof against the host administrator; a database-local hash is not a signature. External append-only logging and automatic audit-table pruning are not implemented. Interactive verification caps each chain at 200,000 rows. Full stopped-workspace and restore verification streams all retained rows; keep independently held anchors.
- Backup: SQLite online snapshots, random salt and nonce, AES-256-GCM authentication/encryption and scrypt-derived recovery keys. Each successful backup has a new versioned filename. Restores authenticate and validate contents before creating a new workspace, refuse overwrite and remove reusable sessions/temporary sign-in state. Schema-7-and-later restores also require the retained local audit chains to verify before publishing restored files. Current format is capped at 256 MB per database. Snapshot/encryption/destination I/O runs outside the API write transaction. Cross-process locks and generation checks protect configuration rotation; failure/overdue and cached destination health are visible. Destination checks run in the background every 30 seconds.
- Local files: Unix database/key/setup/config permissions are owner-only; the data directory is private. Authenticator secrets and the saved backup passphrase are encrypted with a local key. On Windows, use a private user-profile directory with restrictive ACLs; Unix mode bits do not establish Windows ACL isolation.

## Host and deployment responsibilities

The live database is **not fully encrypted by this application**. Enable FileVault, BitLocker or LUKS and protect the operating-system account. A person who controls the host or its database/key files can read or alter HR data, recover accounts and decrypt the saved backup configuration. A compromised running computer is outside the protection of encrypted off-device backups.

Keep both the database and its `.key` together in private local storage. Do not place the live database, key, setup token, backup configuration or identity-provider secrets in a cloud-synced project directory. Back up only encrypted `.opbackup` files to that folder. Keep the backup recovery passphrase off the host, and restrict sharing of the cloud folder.

Use the [remote setup guide](docs/LOCAL_TEAM_AND_BACKUP.md). Configure the exact HTTPS origin, trust the Caddy certificate authority on authorized clients, verify Secure cookies and use individual accounts with MFA. Do not bypass browser certificate warnings. Expose only the VPN listener on a router; keep the application and HTTPS proxy private to the VPN. Public internet hosting, multiple app processes, arbitrary proxy chains and multi-tenant service hosting require a separate deployment design.

Automatic backup runs only while the host and application are awake. A file saved locally is not proof of cloud upload or recoverability. Monitor the sync client, storage quota and backup status; rehearse restore from another device. Retention keeps at least two successful archives per workspace/configuration generation; a new archive must pass a byte-for-byte read-back check before older archives are pruned. Other workspace files and older generations are not automatically pruned. Keep phrases for older generations and monitor quota.

Dependencies are pinned in `uv.lock` and `requirements.txt`; review updates and advisories before upgrading. Payroll, benefits, leave policy, privacy, statutory reporting and retention need relevant domain review before those workflows are relied on operationally. No regulatory compliance is claimed. Remaining capabilities and limits are listed in [the roadmap](docs/ROADMAP.md).

## Reporting a vulnerability

Do not post employee records, secrets, backup files or credentials in public issues. Contact the repository maintainer privately until a dedicated private reporting channel is established.

## Cloud and filing boundaries in 0.4.0

WebDAV destinations/credentials come only from the trusted server environment. TLS checking is enabled, redirects disabled and encrypted filenames/ciphertext bounded. Conditional PUT plus fresh checksum read-back verifies copied bytes. Scheduled transfer runs in a killable child with a 75-second deadline outside local snapshot/configuration/database locks. HTTP users cannot supply destinations or credentials. Local backup success and actual off-device recovery remain separate states. See [cloud setup and limitations](docs/CLOUD_WEBDAV.md).

Employer assignments share employee version preconditions. Payroll captures historical assignments; filing workpapers bind finalized source versions and immutable hashes. Independent reviewers cannot be packet preparers or payroll makers. External receipt status never grants authenticated government acceptance. Complete all-country payroll law is not embedded; [calculation scope](docs/STATUTORY_AND_FILINGS.md) is explicit.

## Access, integrity and service boundaries in 0.5.0

HR can restrict payroll operators to selected employers using recent authentication, CSRF and optimistic grant versions. Saving immediately revokes the target's sessions. Current salaries use current assignments; old pay statements use captured employers. Restricted operators cannot create a workspace-wide run or finalize a run containing hidden statements. HR and auditors retain their administrative scopes, and the basic directory remains shared. Legacy payroll accounts keep their prior workspace-wide scope until HR restricts them. This is not multi-tenant isolation or a general field-permission system. See [enterprise controls](docs/ENTERPRISE_CONTROLS.md).

The private Dex generator accepts matching named TLS certificates, private keys, reviewed provisioned identities and bcrypt hashes with work factors 12–16. Configuration is created exclusively in a new private directory; secrets are never printed. The associated launcher allows only the four expected identity environment variables and requires an explicit HR database. Independent Dex, userspace WireGuard peers and TLS WebDAV recovery passed in disposable same-computer tests. Production accounts, remote networks and off-device storage remain unconfigured; no operating-system network or trust settings were changed. See [service configuration](docs/INDEPENDENT_SERVICES.md).

The restricted SSA file adapter refuses unsupported annual inputs and writes confidential SSNs/PINs to a new owner-only file; it never contacts SSA. No authority acceptance or country-wide regulatory compliance follows from local format tests. Keep its plaintext input/output outside shared/cloud folders and subject them to appropriate encrypted storage and retention controls.

## Period and production controls in 0.6.0

Employer pay groups require matching assignments/country/currency and optimistic worker/group versions. Regular period overlap, worker overlap across group transfers and legacy-month overlap are rejected. Dated results bind exact period values and types, require reviewed external results for every included worker, and retain peer editing and independent finalization. Estimates do not certify a country's tax calculation. Payroll access continues to follow captured employers. See [dated payroll](docs/PAY_PERIODS.md).

The explicit production launch profile checks full database/audit integrity, supported schema, configured HTTPS origin, active real HR, mandatory MFA/HR enrollment, private POSIX files, no demo workers and current scheduled backups. It refuses a listener on failure and prevents disabling mandatory MFA while active. HTTPS configuration is not endpoint/certificate acceptance; same-disk backup completion is not physical-loss protection. Database migration can occur before launch refusal. No production approval is inferred from these checks.

The unauthenticated liveness endpoint exposes only status/version. HR-only online operations uses bounded database queries and cached destination status; expensive integrity/audit/destination checks remain startup/offline operations. Crash supervision has bounded retries, private logs and workspace locking; it signals only its own child process group. It does not install an OS service or restart after reboot. Remaining capacity, off-device, platform and independent assurance requirements still apply. See [operations](docs/OPERATIONS.md).
